# 5. UI/UX设计

## 5.0 UI视觉基准（给Agent）

UI目标是 **Dead Cells式现代像素风**：像素骨架清晰、信息密度高、反馈干脆，允许少量现代光影和粒子增强质感，但不能做成网页落地页、手游抽卡页、玻璃拟态弹窗或SaaS仪表盘。

| 维度 | 设计要求 |
|------|----------|
| 形状 | 硬边像素框，0~4px低圆角，1~2px像素描边，避免大圆角卡片 |
| 纹理 | 使用像素纹理、抖动、断裂边、扫描线或低分辨率噪声；禁止模糊毛玻璃 |
| 色彩 | 暗底高对比，重点色饱和但面积克制；避免大面积柔和渐变和单一紫蓝科技风 |
| 字体与图标 | 像素字体或硬边窄体字；图标优先位图/像素化轮廓，不使用通用网页线性图标作为主视觉 |
| 动效 | 短促、分段、带像素跳帧感；按钮反馈以闪白、描边、轻微位移为主 |
| 特效 | 允许像素粒子、裂隙光、低分辨率辉光；禁止装饰性渐变球、散景光斑、大片软阴影 |
| 布局 | HUD紧凑贴边，战斗视野优先；菜单和奖励界面像游戏内界面，不像网站卡片栅格 |

## 5.1 信息架构

### 5.1.1 信息分类与优先级

游戏运行时向玩家传达的信息分为四大类，每类内部按优先级排序。优先级决定了HUD位置、视觉权重和遮挡关系——高优先级信息始终可见，低优先级信息在非必要时淡出。

| 类别 | 优先级 | 信息项 | 始终可见 | 说明 |
|------|--------|--------|----------|------|
| **战斗信息** | P0 | HP条 | 是 | 生存状态，0.3秒内任何变化必须反馈 |
| 战斗信息 | P0 | 受击方向指示器 | 否(受击时) | 屏幕边缘红色闪光，指示伤害来源方向 |
| 战斗信息 | P1 | 闪避次数 | 是 | 战斗核心资源，清空时闪烁预警 |
| 战斗信息 | P1 | 时之能量条 | 是 | 核心机制资源，<20%预警 |
| 战斗信息 | P1 | 敌人HP条 | 否(锁定时) | 锁定/近距离时显示，Boss常驻 |
| 战斗信息 | P2 | 连击计数 | 否(战斗中) | 连击≥5时显示，3秒未命中淡出 |
| 战斗信息 | P2 | 伤害数字 | 否(命中时) | 飘字，0.8秒淡出 |
| 战斗信息 | P2 | 状态效果图标 | 否(有debuff时) | 敌人头顶或HP条旁 |
| **角色状态** | P1 | 武器图标+状态 | 是 | 当前武器、弹药/蓄力/连击状态 |
| 角色状态 | P1 | 祝福图标区 | 否(按住查看) | 最多8个，紧凑排列，按住LB展开 |
| 角色状态 | P2 | 诅咒图标区 | 否(按住查看) | 最多5个，紫色边框区分 |

| 系统信息 | P3 | FPS/帧率 | 否(开发模式) | 仅Debug模式显示 |
| 系统信息 | P3 | 提示信息 | 否(触发时) | 屏幕下方居中，2秒淡出 |

### 5.1.2 信息展示时机规则

| 状态 | 显示策略 | 说明 |
|------|----------|------|
| 战斗中(有敌对目标) | 全部P0-P1可见，P2战斗信息可见 | 信息密度最高 |
| 战斗中(无敌对目标) | P0可见，P1每3秒脉冲1次，P2淡出 | 战斗间歇喘息 |
| 非战斗(探索) | P0-P1半透明(alpha=0.5)，小地图放大至160×160px | 突出探索信息 |
| 暂停/菜单 | HUD隐藏，仅菜单UI | 避免信息干扰 |
| 过场/对话 | 仅角色状态P1保留(半透明) | 沉浸叙事 |
| 受伤瞬间 | HP条闪白0.1秒→红色脉冲0.3秒，屏幕边缘红色晕影(alpha=0.2)0.5秒 | 强反馈 |
| 濒死(HP<20%) | HP条脉冲2Hz，屏幕边缘持续红色晕影(alpha=0.15)，心跳音效 | 持续预警 |

### 5.1.3 信息冲突解决规则

当多条信息竞争同一视觉区域时：

1. **HP条 > 能量条 > 闪避次数**：从左到右排列，永不遮挡
2. **伤害数字优先级**：暴击伤害(大号金色) > 普通伤害(白色) > 持续伤害(小号灰色)
3. **状态图标冲突**：Debuff图标显示在角色头顶，Buff图标显示在HP条旁，互不干扰
4. **屏幕中央区域**：仅用于时间停止/回溯等核心机制的全屏提示，不用于常规信息

# 6. 美术与音效

## 6.1 美术风格指南

### 6.1.1 核心风格定义

**"Dead Cells式现代像素风：像素骨架 + 克制现代光影"**

角色和环境使用低分辨率像素贴图(角色32×32~64×64基础尺寸，环境16×16瓦片)，保持硬边轮廓、清晰剪影和可读像素纹理。可以叠加Godot 2D灯光、法线贴图、像素粒子和低强度后处理，但这些效果必须服务于像素质感和战斗可读性，不能覆盖像素网格，也不能形成写实、柔焦或网页视觉。

UI同样遵循现代像素风：面板、按钮、边框、图标和装饰线都应具备硬边像素结构；禁止玻璃拟态、大面积模糊半透明、圆角SaaS卡片、装饰性渐变球、散景光斑和营销页式构图。

**参考视觉锚点**：
- Dead Cells：最高优先级。参考其像素角色、流畅动画、现代光影、紧凑动作HUD和不干扰战斗的奖励界面。
- Hyper Light Drifter：次优先级。参考其色彩叙事、像素克制、清晰块面和极简图形语言。
- Hades：只参考战斗信息清晰度、奖励节奏和反馈强度；不参考其手绘UI视觉、厚重装饰框和非像素化界面风格。

### 6.3.2 BGM分层结构

每层BGM包含4个独立音轨层，根据游戏状态动态混合：

| 层级 | 名称 | 触发条件 | 内容 |
|------|------|----------|------|
| Layer 0 | 环境层 | 始终播放 | 基础Pad + 环境音 + 低频脉动 |
| Layer 1 | 探索层 | 非战斗 | 旋律 + 轻打击 + 氛围音色 |
| Layer 2 | 战斗层 | 战斗中 | 节奏组 + Bass + 强打击 + 主旋律变奏 |
| Layer 3 | 高潮层 | Boss/高强度战斗 | 全编制 + 额外合成 + 合唱/人声 |

**混合规则**：
- 进入战斗：Layer 1→0.3秒淡出，Layer 2→0.5秒淡入
- 退出战斗：Layer 2→1.0秒淡出，Layer 1→1.5秒淡入
- Boss出现：Layer 0+2持续，Layer 3→1.0秒淡入
- 时间停止：所有层→0.2秒低通滤波(cutoff=800Hz)，0.2秒后恢复正常
- 时间回溯：所有层→0.5秒反向播放效果+pitch下降2半音→恢复
- 时间加速：所有层→pitch上升1半音+节奏加速1.3×

### 6.3.3 Boss动态音乐系统

采用Vertical Remixing + Horizontal Sequencing混合方案：

**Vertical Remixing（垂直分层）**：Boss BGM分为4层，根据Boss阶段实时混合

| Boss阶段 | Layer 0 | Layer 1 | Layer 2 | Layer 3 |
|----------|---------|---------|---------|---------|
| 阶段1 (HP 100-70%) | 环境Pad ✓ | 基础节奏 ✓ | — | — |
| 阶段2 (HP 70-40%) | 环境Pad ✓ | 增强节奏 ✓ | 弦乐主题 ✓ | — |
| 阶段3 (HP 40-10%) | 环境Pad ✓ | 急促节奏 ✓ | 弦乐+Brass ✓ | 合唱 ✓ |
| 狂暴 (HP <10%) | 失真Pad ✓ | 双倍节奏 ✓ | 全编制 ✓ | 合唱+合成Lead ✓ |

**Horizontal Sequencing（水平序列）**：特殊事件触发短音乐片段(stinger)

| 事件 | Stinger | 长度 | 说明 |

# 7. 技术规格

## 7.1 引擎选择

### 7.1.1 引擎选型结论

本项目技术方案从 Unity 2022 LTS + URP 调整为 **Godot 4.x + GDScript**。核心原因是项目目标是 2D 像素风动作肉鸽，而 Godot 的场景、资源、脚本和配置以文本文件为主，更适合 Git diff、代码审查、自动化脚本和智能体协作。

| 维度 | Godot 4.x 决策 | 说明 |
|------|----------------|------|
| 2D渲染 | 采用 Godot 原生 2D 管线 | TileMap、CanvasItem Shader、Light2D、粒子和后处理足以支撑像素风+现代光影 |
| 像素风适配 | 采用项目级 Pixel Perfect 规范 | 固定设计分辨率、整数缩放、禁用纹理过滤、统一导入预设 |
| 智能体协作 | 优先文本资产和代码可读性 | `.gd`、`.tscn`、`.tres`、`.godot` 均可被智能体直接读取和修改 |
| 数据驱动 | 使用 Resource / `.tres` / JSON | 道具、敌人、祝福、诅咒、房间模板、数值表均数据化 |
| 性能 | GDScript 实现主体，热路径可下沉 | 战斗判定、寻路、回放压缩等瓶颈可用 C++ GDExtension |
| 发布 | Godot Export Preset + Steamworks 插件 | CI 可 headless 构建 Windows 包，后续接 Steam 上传流程 |
| 团队成本 | 无授权费用，工具链轻 | 更适合小团队和 AI 辅助的快速迭代 |

### 7.1.2 推荐方案

**推荐：Godot 4.x + GDScript**

**核心理由**：

1. **2D像素游戏的工程模型更直接**：节点、场景、TileMap、动画、输入、UI 都是 Godot 原生工作流，减少 Unity Editor / Prefab / Import Pipeline 的隐式状态。
2. **更适合智能体开发**：Godot 的脚本和场景资源更容易被文本方式审查和修改，智能体可以通过文件 diff 精准理解改动。
3. **玩法原型速度更快**：GDScript 编译链短，编辑-运行反馈快，适合先做战斗手感、时间操控和地牢垂直切片。
4. **技术复杂度可控**：当前目标是 2D/2.5D 俯视角，不需要 Unity URP/DOTS 的复杂能力；性能风险可通过对象池、空间分区、MultiMesh/GPUParticles2D 和 GDExtension 局部解决。

**Unity的备选场景**：
- 如果后续转向大量3D场景、复杂商业中间件或大型外包资源管线，可重新评估 Unity。
- 如果团队已有成熟 Unity 工程资产和专职 Unity 技术美术，迁回 Unity 才有明显收益。

**技术栈确认**：
- 引擎：Godot 4.x
- 语言：GDScript 2.0
- 可选原生扩展：GDExtension / C++（仅用于性能瓶颈）
- 渲染：Godot 2D Renderer + CanvasItem Shader + Light2D + GPUParticles2D
- 音频：Godot AudioServer / AudioStreamPlayer / AudioBus（动态音乐通过自研分层控制）
- 版本控制：Git + Git LFS (二进制资源)
- CI/CD：GitHub Actions + Godot Headless Export
